# DITA 0.2.0 — Архитектура платформы

## Назначение

DITA — самостоятельная платформа в парадигме «платформа + конфигурация», ориентированная на концепции 1С 7.7 без буквального копирования реализации. GigaWatt — первая прикладная конфигурация; её предметные сущности и правила не входят в ядро DITA. Исторические документы и Git-история DITA 0.1.0 сохраняются.

## Принципы

1. Meta — ядро платформы: стандартные типы, метаданные, реквизиты, ссылки, нумерация и жизненный цикл.
2. Go + PostgreSQL, SQL-first, pgx, явный SQL, `net/http`, `slog`, модульный монолит.
3. Типизированные физические таблицы/колонки; EAV не используется как основное хранилище.
4. Внутренний `id BIGINT` отделён от бизнес-кода/номера.
5. Конфигурация декларативна, версионируема, не содержит SQL или исполняемого кода.
6. PostgreSQL закрепляет целостность через PK/FK/NOT NULL/CHECK/UNIQUE/индексы/транзакции.
7. Установка и обновление конфигурации — отдельная контролируемая операция; Runtime не выполняет DDL.
8. Потеря/преобразование данных не выполняется молча.

## Логические слои

```text
Конфигурация (первая — GigaWatt)
          |
          v
JSON parser + validator
          |
          v
Configuration planner (dry-run)
          |
          v
Configuration installer / updater
          |
          v
Application services / Runtime
          |
          v
Meta Core + PostgreSQL
```

- **API Layer:** HTTP transport, входная валидация, вызов сценариев; без SQL и предметных правил.
- **Application Layer:** use cases, транзакционные границы, команды жизненного цикла.
- **Meta Core:** модели конфигурации, типов, атрибутов, ссылок, нумерации, установщика и планировщика.
- **Runtime:** операции с объектами установленных типов; использует метаданные и типизированные таблицы.
- **Infrastructure:** pgx, SQL, транзакции, миграции и slog.

## Стандартные типы

Meta предусматривает `catalog`, `document`, `planning`, `task`, `note`. Наличие типа в метамодели не означает необходимость немедленно создавать отдельную подсистему. Task и Note имеют минимальный стандартный набор полей, заданный в `DATA_MODEL_DITA_0.2.0.md`; workflow, вложения и rich text не входят в первую реализацию.

## Конфигурация и физическая схема

- Формат — UTF-8 JSON с `format_version`, UUID конфигурации/типов/реквизитов, SemVer версии конфигурации и диапазоном совместимости с платформой.
- Строгая валидация завершается до DDL: неизвестные поля, дубли ID, неизвестные типы, циклические/неразрешённые ссылки и неподдерживаемые версии отклоняются.
- Схемы PostgreSQL: `meta` для реестра и системных данных; `data` для таблиц объектных типов; `public.schema_migrations` сохраняется как реестр существующего migration runner.
- Таблица типа: `data.o_<uuid_without_hyphens>`; колонка реквизита: `a_<uuid_without_hyphens>`. Физические имена не зависят от display name/code.
- Типы реквизитов ограничены явным перечнем: `string`, `text`, `integer`, `decimal`, `boolean`, `date`, `datetime`, `reference`.
- Конфигурация задаёт структуру и ограничения декларативно; SQL идентификаторы строятся только из проверенных UUID, значения передаются параметрами.
- Установщик строит dry-run plan, затем под advisory lock создаёт таблицы, индексы и FK в детерминированном порядке.

## Первая схема Meta

Минимальные таблицы: `meta.actors`, `meta.configurations`, `meta.configuration_versions`, `meta.object_types`, `meta.attributes`, `meta.number_counters`. Исходный JSONB версии является каноническим документом; нормализованные типы/атрибуты — индекс метаданных для Runtime и DDL. Отдельная таблица индексов в первой схеме не нужна: их определения воспроизводятся из проверенного JSON.

`meta.actors` — минимальная цель FK для `created_by`, `updated_by`, `task.assignee_id`. IAM (пароли, сессии, роли, права) не реализуется. Авторские поля nullable; `assignee_id` у Task обязателен.

## Нумерация и жизненный цикл

- Catalog code: BIGINT от 1 внутри типа справочника.
- Document number: BIGINT от 1 внутри типа документа и календарного года `created_at` в `Europe/Moscow`.
- Planning number: BIGINT от 1 внутри типа плана и календарного года `created_at` в `Europe/Moscow`; даты периода не влияют на год номера.
- Счётчик резервируется транзакционным UPSERT/row lock; `MAX()+1` запрещён; уникальность закреплена в PostgreSQL; номера после soft delete не переиспользуются.
- Общие системные поля: `id`, `created_at`, `updated_at`, `created_by`, `updated_by`, `deleted_at`. `deletion_mark` не применяется.
- Ссылки — типизированные FK; физическое удаление самостоятельных объектов по умолчанию RESTRICT; soft delete не каскадирует.
- Проведение/отмена — отдельные транзакционные операции; проведение блокирует изменение/удаление, отмена компенсирует последствия.

## Эволюция конфигурации

Обновление начинается с dry-run плана. Add type и nullable attribute — безопасные изменения. Required, смена типа/длины вниз, смена ссылки, удаление атрибута/типа требуют проверки данных и явного плана. UUID не меняются при rename. Удалённые поля по умолчанию деактивируются, физические колонки сохраняются. Destructive DDL не генерируется автоматически.

## Технологические и предметные ограничения

Не вводить ORM, Docker, микросервисы, generic EAV, универсальную workflow/IAM/audit подсистему, табличные части, регистры, вложения или GigaWatt-специфику без отдельного решения. Существующий migration runner создаёт `public.schema_migrations` и применяет `.up.sql` в транзакции; миграции приложения остаются forward-only.
