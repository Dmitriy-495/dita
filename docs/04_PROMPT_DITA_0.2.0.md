# Стартовый промпт — DITA 0.2.0

Брат, продолжаем самостоятельный проект DITA. Работаем только над платформой DITA; GigaWatt — отдельное прикладное решение и не должен проникать в ядро DITA.

## Режим работы

- Сначала изучи фактический репозиторий, исходники, миграции, тесты, документацию и историю Git.
- Не делай выводов о реализации по одним документам: подтверди состояние кодом и схемой БД.
- Сначала представь короткий план, затрагиваемые файлы, риски миграции и неразрешённые вопросы.
- Не меняй код, миграции или файлы проекта, пока пользователь явно не напишет `ЖГИ`.
- После `ЖГИ` выполняй работу небольшими последовательными шагами, без лишней дискуссии и несогласованных расширений scope.
- Не переписывай применённые миграции. Используй новые forward-only миграции.
- Не добавляй лишние зависимости, универсальные абстракции или ненужные документы/тестовые этапы.
- Сохраняй стиль проекта; комментарии в Go-коде пиши по-русски.
- В конце показывай реальные команды и результаты проверок, не утверждай о проверках, которые не запускались.

## Цель DITA 0.2.0

Сверяйся с `CHECKPOINT_003.md` и `ITERATION_003_CHECKLIST.md`. Целевой объём включает:

1. Общие системные реквизиты: `id`, `created_at`, `updated_at`, `created_by`, `updated_by`, `deleted_at`.
2. `TIMESTAMPTZ` для временных полей; фиксированная timezone `Europe/Moscow` для календарного года.
3. Soft delete через `deleted_at`; обычные чтения исключают удалённые записи.
4. Числовые `BIGINT`-коды элементов справочников; нумерация отдельно внутри каждого справочника, начиная с 1; номера после soft delete не переиспользуются.
5. Отдельная нумерация Document и Planning по типу и календарному году, вычисляемому из `created_at` в `Europe/Moscow`.
6. Task: системные поля, `description TEXT`, обязательный `assignee_id`, `status`, необязательный `due_at TIMESTAMPTZ`, `result TEXT`, платформенный `completed_at`; статусы `new`, `in_progress`, `completed`, `cancelled`; завершение требует непустого результата; просрочка не завершает задачу автоматически; отмена не равна удалению.
7. Note: системные поля, `description TEXT`, `important BOOLEAN NOT NULL DEFAULT false`; без title, вложений, rich text и истории версий.

## Важные границы

- Не создавать generic numbering subsystem.
- Не придумывать поля и lifecycle Document/Planning сверх согласованного: сначала изучить фактическое состояние, неизвестное вынести на согласование.
- Не выполнять автоматическую/разрушительную конвертацию уже существующих строковых кодов. Сначала обследовать данные и подготовить безопасный план миграции, отдельно согласовать его.
- Поля `created_by`, `updated_by` и `assignee_id` должны соответствовать существующей модели actor/user. Не создавать полноценную IAM без согласования.
- Целевые требования не означают, что они уже реализованы.
