# DITA 0.2.0 — Checkpoint 003

## Цель итерации

Подготовить DITA к следующему согласованному этапу развития системных реквизитов, идентификаторов и прикладных объектов. Перед изменением реализации обязательно изучить фактический код, схему PostgreSQL, миграции и историю Git. Документ задаёт целевой объём, но не утверждает, что перечисленное уже реализовано.

## Объём DITA 0.2.0

### 1. Системные реквизиты

Единый целевой набор системных реквизитов:

- `id`
- `created_at`
- `updated_at`
- `created_by`
- `updated_by`
- `deleted_at`

Временные поля используют PostgreSQL `TIMESTAMPTZ`. Для вычислений, связанных с календарным годом, на этом этапе применяется фиксированная timezone `Europe/Moscow`. Авторские поля должны использовать уже существующую модель идентификации actor/user; не создавать полноценную IAM без отдельного согласования.

### 2. Soft delete

- Логическое удаление фиксируется через `deleted_at`.
- `deleted_at IS NULL` означает активную запись.
- Обычные чтения не должны возвращать логически удалённые записи.
- Удаление не должно приводить к повторному использованию уже выданных числовых номеров.
- Миграции только forward-only: не редактировать миграции, которые могли быть применены.

### 3. Элементы справочников

- Числовой код элемента — `BIGINT`.
- Нумерация начинается с 1 и ведётся отдельно внутри каждого справочника.
- Номер не переиспользуется после soft delete.
- Не вводить универсальную подсистему нумерации.
- До миграции существующих строковых кодов требуется обследовать текущую схему и данные и подготовить безопасный план преобразования. Не выполнять разрушительную конвертацию автоматически.

### 4. Document и Planning

Для типов `Document` и `Planning` предусматривается отдельная нумерация по типу и календарному году. Год определяется из `created_at` в timezone `Europe/Moscow`. Не объединять счётчики разных типов или разных лет.

Полная схема реквизитов, бизнес-поля и жизненный цикл Document/Planning этим checkpoint не определены. Не придумывать их; сначала зафиксировать обнаруженную реализацию и вынести неразрешённые решения на согласование.

### 5. Task

Целевые поля сверх системных реквизитов:

- `description TEXT`
- обязательный `assignee_id`
- `status`
- необязательный `due_at TIMESTAMPTZ`
- `result TEXT`
- `completed_at TIMESTAMPTZ`, назначаемый платформой

Статусы: `new`, `in_progress`, `completed`, `cancelled`.

Правила:
- Переход в `completed` разрешён только при непустом `result`.
- `completed_at` устанавливает платформа, а не клиент.
- Просрочка (`due_at` в прошлом) сама по себе не завершает задачу.
- `cancelled` не является удалением.
- `assignee_id` обязателен. Его связь должна соответствовать реально существующей модели пользователей/акторов; не изобретать отдельную IAM.

### 6. Note

Целевые поля сверх системных реквизитов:

- `description TEXT`
- `important BOOLEAN NOT NULL DEFAULT false`

Не добавлять `title`, вложения, rich text или историю версий без отдельного согласования.

## Ограничения реализации

- Не менять предметный scope DITA на предметный scope GigaWatt.
- Не добавлять generic numbering subsystem.
- Не менять применённые миграции; новые изменения оформлять новыми forward-only миграциями.
- Не преобразовывать существующие строковые коды до изучения реальных данных и согласования стратегии миграции.
- Не считать пункты этого документа уже реализованными.
- Не начинать реализацию до явного подтверждения пользователя `ЖГИ`.

## Обязательный первый шаг следующей сессии

1. Проверить `git status`, текущую ветку и `git log`.
2. Изучить структуру проекта, актуальные исходники, все миграции и тесты.
3. Проверить текущие типы/форматы кодов и наличие данных, на которые повлияют изменения.
4. Сопоставить фактическое состояние с этим checkpoint.
5. Представить короткий план изменений и перечень рисков/неразрешённых решений. Код не менять до отдельного `ЖГИ`.

## Завершение итерации

Итерация считается завершённой только после реализации согласованного объёма, успешных проверок, актуализации документации и публикации следующего `CHECKPOINT_*.md`. Фактические результаты и команды проверки должны быть записаны в checkpoint следующей итерации.
