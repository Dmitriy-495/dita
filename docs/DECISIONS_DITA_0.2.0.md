# DITA 0.2.0 — Реестр архитектурных решений

Статусы: **Принято** — инвариант обязателен для проектирования и реализации. **Отложено** — не входит в текущий минимальный объём.

## ADR-0001 — Платформа и конфигурация
**Статус:** Принято.

DITA — самостоятельная платформа. GigaWatt — отдельная прикладная конфигурация и не входит в Meta Core.

## ADR-0002 — Meta как ядро и стандартные типы
**Статус:** Принято.

Meta определяет `catalog`, `document`, `planning`, `task`, `note`, метаданные, реквизиты, ссылки, нумерацию и базовый жизненный цикл. Специализированные подсистемы не создаются автоматически только из-за наличия стандартного типа.

## ADR-0003 — SQL-first и типизированное хранение
**Статус:** Принято.

Для каждого сохраняемого типа конфигурации создаётся отдельная физическая таблица PostgreSQL с типизированными колонками. Универсальная EAV-таблица не используется как основное хранилище.

## ADR-0004 — ID отделён от бизнес-номера
**Статус:** Принято.

`id BIGINT` — технический PK/FK. Бизнес-код/номер — отдельное поле и никогда не используется как идентификатор ссылки.

## ADR-0005 — Бизнес-нумерация
**Статус:** Принято.

- Catalog code: BIGINT от 1 внутри конкретного типа справочника.
- Document number: BIGINT от 1 внутри типа документа и календарного года `created_at` в `Europe/Moscow`.
- Planning number: BIGINT от 1 внутри типа плана и календарного года `created_at` в `Europe/Moscow`; даты периода не влияют на год номера.
- Номер резервируется транзакционным счётчиком/блокировкой; `MAX()+1` запрещён.
- Уникальные ограничения БД являются последней защитой; soft delete и физическое удаление не освобождают номер.

## ADR-0006 — Общие системные поля и soft delete
**Статус:** Принято.

Общие поля самостоятельного объекта: `id`, `created_at`, `updated_at`, `created_by`, `updated_by`, `deleted_at`. Все временные значения — `TIMESTAMPTZ`. `created_by`/`updated_by` nullable, если actor-контекст отсутствует. Каноническое поле удаления — `deleted_at`; термин `deletion_mark` из ранней редакции модели считается устаревшим и не используется в DITA 0.2.0.

## ADR-0007 — Минимальный Actor, без IAM
**Статус:** Принято.

`meta.actors` — минимальная таблица для ссылок авторства и исполнителя Task. Аутентификация, пароли, сессии, роли и разрешения отложены. Не создавать фиктивного системного actor. `task.assignee_id` обязателен и ссылается на actor.

## ADR-0008 — Формат конфигурации
**Статус:** Принято.

Конфигурация — строгий версионируемый UTF-8 JSON, `format_version="1"`, версия конфигурации SemVer. UUID конфигурации, типов и атрибутов стабильны между версиями. Неизвестные поля, дубли ID, неизвестные типы и неразрешённые ссылки отклоняются до DDL. SQL/код/выражения в конфигурации запрещены.

## ADR-0009 — Физические имена и схемы PostgreSQL
**Статус:** Принято.

Схемы: `meta` для реестра/системных данных, `data` для объектных таблиц. Имя таблицы `data.o_<uuid_without_hyphens>`, имя колонки `a_<uuid_without_hyphens>`. Имена строятся из валидированных UUID, а не из отображаемых имён. Существующий migration runner использует `public.schema_migrations`; в рамках Iteration 001 его не переименовывать.

## ADR-0010 — Реестр конфигураций и метаданных
**Статус:** Принято.

Минимальные таблицы: `meta.configurations`, `meta.configuration_versions`, `meta.object_types`, `meta.attributes`, `meta.actors`, `meta.number_counters`. Исходный JSONB каждой версии — канонический документ. Нормализованные object_types/attributes — индекс для Runtime и DDL. Отдельная таблица индексов не нужна до доказанной потребности.

## ADR-0011 — Ссылки и удаление
**Статус:** Принято.

Ссылки реализуются FK на `id` конкретной физической таблицы; полиморфные ссылки запрещены. Самостоятельные объекты по умолчанию физически удаляются только при отсутствии входящих ссылок (`RESTRICT`). Soft delete не каскадирует. Каскад допустим только для композиционных дочерних строк, если они будут отдельно введены.

## ADR-0012 — Проведение и отмена
**Статус:** Принято.

Проведение и отмена проведения — отдельные транзакционные команды. Проведение валидирует данные/ссылки и фиксирует последствия вместе со статусом. Отмена компенсирует последствия; объект нельзя редактировать/удалять до отмены. Универсальный workflow и регистры не входят в первую схему.

## ADR-0013 — Task и Note
**Статус:** Принято.

Task: `description`, обязательный `assignee_id`, `status` (`new|in_progress|completed|cancelled`), nullable `due_at`, `result`, платформенный `completed_at`. Завершение требует непустой result; просрочка не завершает задачу; cancelled не равно удалению.

Note: только `description` и `important BOOLEAN NOT NULL DEFAULT false` сверх общих системных полей. Title, вложения, rich text и version history не вводятся.

## ADR-0014 — Безопасная эволюция конфигурации
**Статус:** Принято.

Каждое обновление начинается с dry-run плана под advisory lock. UUID сохраняются при переименовании. Nullable-атрибуты можно добавлять автоматически; required-атрибут требует проверки/backfill. Смена типа, уменьшение длины, смена target и удаление данных не преобразуются автоматически. Удаление атрибута/типа по умолчанию деактивирует метаданные и сохраняет физические данные. Destructive operation требует отдельного явного плана и подтверждения.

## ADR-0015 — Стек и модульный монолит
**Статус:** Принято.

Go, PostgreSQL, pgx, явный SQL, `net/http`, `slog`, миграции SQL. ORM, Docker, микросервисы и лишние зависимости не добавляются без обоснования.

## ADR-0016 — История и база данных
**Статус:** Принято.

Исторические документы DITA 0.1.0 и Git history сохраняются. Старая схема/данные не переносятся автоматически. SQL migrations forward-only. Сброс БД возможен только после отдельной проверки точного имени целевой БД и подтверждения, что это не `giga_watt` и не другая БД GigaWatt.

## Открытые детали реализации (не меняют ADR)

- Конкретный SQL DDL и миграционный baseline новой чистой схемы.
- Точная реализация builder/planner и формата ошибок валидации.
- Набор интеграционных тестов установщика, FK и конкурентной нумерации.
- Механизм хранения/проверки checksum конфигурации и блокировки установки.
- Конкретные бизнес-правила проведения для каждого прикладного типа.

Эти детали должны быть реализованы в следующих итерациях без нарушения принятых инвариантов.
