# DITA 0.1.0 — Техническое задание

## 1. Назначение
DITA — независимая программная платформа для создания прикладных информационных систем посредством конфигурирования мета-объектов.

DITA не является частью конкретной предметной системы. Первым прикладным решением на DITA является GigaWatt-3.

Концептуальный ориентир — философия 1С:Предприятие 7.x: платформа предоставляет механизмы, прикладная система создаётся посредством конфигурации. DITA не копирует архитектуру 1С и использует современные технологии.

## 2. Главная идея
DITA разделяет:
1. описание прикладной системы;
2. выполнение прикладной системы;
3. данные конкретного приложения.

```text
Мета-объект
    ↓
Конфигурация
    ↓
Runtime
    ↓
Конкретные данные
```

## 3. Независимость
DITA не содержит предметных сущностей GigaWatt, ЖКХ-специфичных правил, зависимости от GigaWatt-3, dtool или конкретного frontend.

## 4. Технологические принципы
- Go
- PostgreSQL
- HTTP API
- SQL-first
- modular monolith
- минимальное количество зависимостей
- Docker не является обязательным
- типизированная модель данных
- ORM не является архитектурным центром
- EAV не является основной моделью хранения

Не допускается создание универсального framework-for-framework.

## 5. Meta-Layer
Meta-Layer является частью самой DITA.

Начальный набор типов:
- Справочники
- Документы
- Перечисления
- Отчёты
- Обработки
- Журналы документов
- Константы

## 6. Справочники
Мета-описание:

```text
id
name
prefix
```

Элемент справочника:

```text
id
code
name
```

`id` — технический bigint. `code` — информативный бизнес-код, формируемый из префикса и числового идентификатора.

Пример: `ОО-000001`.

## 7. Системные реквизиты
Общий набор:

```text
id
created_at
updated_at
created_by
updated_by
deleted_at
```

DITA автоматически предоставляет и обслуживает эти реквизиты.

## 8. Soft delete
`deleted_at = NULL` означает активный объект. Заполненный `deleted_at` означает логически удалённый объект. Обычные чтения не возвращают удалённые объекты.

## 9. Пользователи
Нужна минимальная модель пользователя для `created_by`, `updated_by`, будущего контроля доступа и идентификации операции. Полноценная IAM-система в 0.1.0 не требуется.

## 10. Конфигурация
Ключевая задача — создавать прикладные системы посредством конфигурирования мета-объектов.

Пример:

```text
Создать справочник "Объекты эксплуатации"
Добавить реквизит "Адрес"
Добавить реквизит "Тип объекта"
```

DITA не должна превращаться в EAV-конструктор.

## 11. Runtime
Runtime отвечает за загрузку конфигурации, создание/чтение/изменение объектов, soft delete, системные реквизиты, базовые правила мета-объектов и HTTP API.

## 12. API
HTTP API — основной внешний интерфейс. Клиенты не обращаются напрямую к PostgreSQL.

```text
DITA
 ├── Web UI
 ├── CLI / dtool
 └── другие клиенты
```

## 13. Ограничения
Без отдельного архитектурного решения запрещены EAV как основная модель, универсальная сущность с бесконечными свойствами, `map[string]any` вместо модели, ORM как центр архитектуры, попытка реализовать всю 1С, код GigaWatt и frontend внутри ядра.

## 14. Развитие
Разработка маленькими вертикальными шагами: цель → реализация → тест → проверка → Git checkpoint → документация.

## 15. DITA 0.1.0
Цель — доказать, что DITA может описывать и выполнять простое приложение посредством Meta-Layer.

Контрольный сценарий:

```text
Создать Meta Catalog "Объекты эксплуатации"
        ↓
получить Runtime Catalog
        ↓
создать элемент
        ↓
ОО-000001 "Котельная №1"
        ↓
прочитать
        ↓
изменить
        ↓
soft delete
```

## 16. Критерий успеха
DITA 0.1.0 успешна, если прикладная структура создаётся средствами платформы, работает через API, описывается Meta-Layer, Runtime работает по конфигурации, системные реквизиты обслуживаются платформой, данные типизированы, PostgreSQL остаётся источником данных, а клиент не зависит от внутренних пакетов DITA.
