# DITA 0.2.0 — Модель данных

## 1. Классы данных

- **Системные данные:** настройки платформы, версии схемы, конфигурации и их установки; минимальные записи акторов для авторства.
- **Метаданные:** конфигурации, виды объектов, реквизиты, типы значений, ссылки, ограничения и правила нумерации.
- **Прикладные данные:** элементы справочников, документы, планы, задачи, заметки и другие объекты конфигурации. Они хранятся в типизированных таблицах PostgreSQL, а не в универсальной EAV-таблице.

## 2. Внутренний ID и бизнес-номер

- Каждый сохраняемый объект имеет внутренний `id bigint`.
- ID технический, стабилен в течение жизни объекта и используется в ссылках.
- Бизнес-код/номер — отдельное поле с правилами конкретного стандартного типа.
- Бизнес-номер не используется как PK или FK.
- Уже выданные номера не переиспользуются. Исправление номера не должно приводить к повторной выдаче старого номера другому объекту.

## 3. Бизнес-нумерация

| Тип | Поле номера | Область нумерации | Начало |
|---|---|---|---:|
| Элемент справочника | `code bigint` | Вид справочника | 1 |
| Документ | `number bigint` | Вид документа + календарный год | 1 |
| План | `number bigint` | Вид плана + календарный год | 1 |

Календарный год для документов и планов определяется по дате самого объекта в часовом поясе `Europe/Moscow`. Номер — числовая часть; формат отображения не меняет правила уникальности.

Генерация должна быть атомарной и безопасной при параллельном создании. Запрещено использовать `MAX(number) + 1` без синхронизации. Реализация использует транзакционный счётчик/блокировку и уникальное ограничение на область нумерации. Выданные номера не переиспользуются при удалении объекта. Перенос объекта в другой год или изменение уже выданного номера не должны выполняться незаметно; правила корректировки фиксируются отдельной операцией с сохранением целостности и аудита.

## 4. Системные поля

### Общие поля сохраняемого объекта

| Поле | Тип | Правило |
|---|---|---|
| `id` | `bigint` | PK, обязателен, генерируется платформой/БД |
| `created_at` | `timestamptz` | Обязателен, устанавливается сервером |
| `updated_at` | `timestamptz` | Обязателен для изменяемых объектов; обновляется при изменении |
| `created_by` | `bigint` FK на системного актора | Допускает `NULL` для технического/анонимного контекста, пока actor не установлен; фиктивные ID запрещены |
| `updated_by` | `bigint` FK на системного актора | Допускает `NULL` при отсутствии установленного actor; фиктивные ID запрещены |
| `deletion_mark` | `boolean` | Применяется к самостоятельным прикладным объектам, для которых предусмотрено мягкое удаление; не добавляется механически к каждой технической таблице |

Поля времени выставляются сервером. В первой итерации достаточно минимальной таблицы системных акторов/пользователей для ссылок авторства. Аутентификация, роли и разрешения не входят в этот минимальный объём. До реализации внешней идентификации запросы без actor сохраняют `NULL`, а не используют вымышленного пользователя.

### Поля стандартных типов

- **Справочник:** `code bigint`, представление/наименование; `parent_id` только для иерархии; `is_folder` только для справочника с группами; `owner_id` только для подчинённого справочника.
- **Документ:** дата/время документа, `number bigint`, признак проведения `posted`, если тип поддерживает проведение, и `deletion_mark`.
- **План:** дата или период, `number bigint`; `posted` только если проведение предусмотрено видом плана; `deletion_mark`.
- **Задача и заметка:** системные поля и реквизиты, определённые стандартным типом/конфигурацией; бизнес-номер не добавляется без необходимости.

Не каждое поле входит в каждую таблицу. Физический состав колонок определяется стандартным типом и конфигурацией.

## 5. Конфигурация и физическая схема

Конфигурация хранится в версионируемом JSON и задаёт типы, реквизиты, ссылки и ограничения декларативно. Каждому объекту метаданных присваивается стабильный технический идентификатор. Отображаемые названия могут меняться без переименования физических объектов.

Каждый сохраняемый тип имеет отдельную таблицу, а реквизиты — типизированные колонки. На первом этапе поддерживается ограниченный явный перечень типов: строки ограниченной длины и текст, `boolean`, целые числа, `numeric`, `date`, `timestamptz` и ссылки на объекты платформы. Расширение перечня типов требует изменения Meta и тестов.

Конфигурация не содержит исполняемый SQL. Платформа проверяет структуру, версии, уникальность идентификаторов, типы, ссылки и совместимость; формирует план схемы; изменения применяются версионируемыми миграциями. Обратные/разрушительные преобразования автоматически не генерируются. Потеря данных требует явно заданной миграции.

## 6. Ссылки, удаление и проведение

- **Композиционные дочерние данные** (например, строки табличной части, существующие только внутри владельца) удаляются каскадно вместе с владельцем.
- **Ссылки на самостоятельные объекты** по умолчанию запрещают физическое удаление объекта, пока на него есть ссылки, если конфигурация явно не задаёт безопасное и проверенное поведение.
- **Мягкое удаление** устанавливает `deletion_mark`; оно не равно физическому удалению и не должно автоматически каскадировать на самостоятельные объекты.
- **Физическое удаление** — отдельная операция, разрешённая только при выполнении правил ссылочной целостности.
- **Проведение** — транзакционная операция для поддерживаемых типов: проверка данных и ссылок, применение предусмотренных конфигурацией последствий и фиксация состояния только при успехе.
- **Отмена проведения** — отдельная транзакционная операция, отменяющая последствия проведения и переводящая объект в непроведённое состояние. Она не является удалением.

Правила проведения и обратных действий задаются видом объекта/конфигурацией; универсальный workflow не входит в ядро первой итерации.

## 7. Целостность PostgreSQL

Использовать PK/FK, `NOT NULL`, `CHECK`, уникальные ограничения, индексы и транзакции для закрепления инвариантов. Правила, которые нельзя выразить ограничениями БД, проверяются в прикладном слое и тестах. Схема и миграции должны воспроизводиться на чистой БД.

## 8. Объём первой реализации

Первая итерация реализует минимальные системные таблицы, метаданные конфигурации, стандартные определения типов и управляемое создание типизированных таблиц. Она не реализует прикладную конфигурацию GigaWatt, полноценную авторизацию, универсальный workflow или полный документооборот.
