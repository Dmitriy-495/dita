# DITA 0.2.0 — Модель данных

## 1. Назначение и границы

Документ определяет целевую логическую и физическую модель данных DITA 0.2.0, формат конфигурации и правила её эволюции. DITA остаётся платформой; предметная модель GigaWatt находится в отдельной конфигурации.

Основные инварианты:

- PostgreSQL — источник ограничений целостности; Go использует явный SQL и pgx.
- Прикладные объекты хранятся в отдельных типизированных таблицах. Универсальная EAV-модель не используется.
- Внутренний `id BIGINT` не совпадает с бизнес-кодом/номером.
- Конфигурация декларативна и версионируема; произвольный SQL и исполняемый код запрещены.
- DDL выполняется только установщиком/обновлением конфигурации, не обычным Runtime.
- Автоматическое удаление данных или неявное преобразование типов запрещено.

## 2. Стандартные типы объектов

Meta регистрирует пять стандартных видов. Вид — неизменяемая семантика платформы; конкретный тип внутри конфигурации — экземпляр метаданных со стабильным UUID.

| Вид | Назначение | Стандартные поля сверх общих | Бизнес-нумерация |
|---|---|---|---|
| `catalog` | Справочник и его элементы | `code BIGINT`, `name TEXT`; опционально `parent_id`, `is_folder`, `owner_id` только при включённых свойствах типа | `code` отдельно в пределах вида справочника, с 1 |
| `document` | Документ | `document_at TIMESTAMPTZ`, `number_year SMALLINT`, `number BIGINT`, `posted_at TIMESTAMPTZ NULL` | отдельно по типу документа и году `created_at` в `Europe/Moscow` |
| `planning` | План | `period_start DATE` и/или `period_end DATE` по определению типа, `number_year SMALLINT`, `number BIGINT`; проведение только при явном включении | отдельно по типу плана и году `created_at` в `Europe/Moscow` |
| `task` | Задача | `description TEXT`, `assignee_id BIGINT NOT NULL`, `status`, `due_at TIMESTAMPTZ NULL`, `result TEXT`, `completed_at TIMESTAMPTZ NULL` | нет |
| `note` | Заметка | `description TEXT`, `important BOOLEAN NOT NULL DEFAULT false` | нет |

### 2.1. Общие системные поля

Все сохраняемые самостоятельные объекты имеют:

| Поле | PostgreSQL | Правило |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | Внутренний идентификатор; первая выданная величина — 1 в пределах физической таблицы |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()` | Устанавливает сервер при создании; неизменяем после создания |
| `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()` | Сервер обновляет при каждом успешном изменении |
| `created_by` | `BIGINT NULL` | FK на `meta.actors(id)`; `NULL`, если actor-контекст отсутствует |
| `updated_by` | `BIGINT NULL` | FK на `meta.actors(id)`; `NULL`, если actor-контекст отсутствует |
| `deleted_at` | `TIMESTAMPTZ NULL` | `NULL` — активен; ненулевое значение — soft delete |

`deletion_mark` не используется: каноническое поле DITA 0.2.0 — `deleted_at`, как закреплено в стартовом промпте и CHECKPOINT_003. Технические таблицы метаданных/счётчиков не обязаны иметь эти поля. Все обычные выборки самостоятельных объектов фильтруют `deleted_at IS NULL`. Soft delete не удаляет строку, не освобождает номер и не каскадирует на самостоятельные объекты.

### 2.2. Actor и граница Identity

Минимальная таблица `meta.actors` нужна только как цель FK для авторства и исполнителя задачи:

- `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`;
- `code TEXT NOT NULL UNIQUE` — стабильный технический/внешний код;
- `name TEXT NOT NULL`;
- `is_active BOOLEAN NOT NULL DEFAULT TRUE`;
- `created_at`, `updated_at TIMESTAMPTZ NOT NULL`.

Аутентификация, пароли, сессии, роли, разрешения, группы и синхронизация внешних каталогов не входят в модель. Не создаётся фиктивный системный actor. `created_by`/`updated_by` допускают `NULL`; `task.assignee_id` обязателен и должен ссылаться на существующего активного actor при назначении. Деактивация actor не удаляет его и не нарушает исторические FK.

### 2.3. Правила Task

`status` — ограниченный набор: `new`, `in_progress`, `completed`, `cancelled`. В БД фиксируется `CHECK` на эти значения. Переход в `completed` разрешён только при `result IS NOT NULL AND btrim(result) <> ''`; при переходе платформа устанавливает `completed_at`. При выходе из `completed` платформа очищает `completed_at`. `due_at < now()` не меняет статус автоматически. `cancelled` — самостоятельный бизнес-статус, не удаление. Изменение статуса выполняется сервисной операцией, а не прямым присваиванием клиентского `completed_at`.

### 2.4. Правила Note

У Note только `description TEXT` и `important BOOLEAN NOT NULL DEFAULT FALSE` сверх общих системных полей. Не вводить `title`, вложения, rich text, историю версий или отдельную подсистему заметок.

### 2.5. Документы и планы

`created_at` — системное время создания объекта и единый источник календарного года нумерации для Document и Planning: `EXTRACT(YEAR FROM created_at AT TIME ZONE 'Europe/Moscow')`. Это правило закреплено стартовым prompt и CHECKPOINT_003. `document_at` и даты периода Planning — прикладные реквизиты; они не влияют на год номера. `created_at` неизменяем после создания. Платформа вычисляет и сохраняет `number_year SMALLINT NOT NULL` в той же транзакции, в которой резервирует номер; уникальность задаётся по `(number_year, number)`. Значение `number_year` является снимком года при создании и не меняется при последующих обновлениях. Уникальность номера документа и плана задаётся по `(number_year, number)` в пределах физической таблицы типа.

`posted_at IS NULL` означает непроведённый документ; ненулевое значение — проведённый. Сервис проведения блокирует конкурентное изменение объекта, проверяет реквизиты/ссылки и в одной транзакции применяет предусмотренные конфигурацией последствия и устанавливает `posted_at`. Отмена проведения — отдельная транзакция, которая компенсирует последствия и очищает `posted_at` только при успешной компенсации. Проведённый объект нельзя редактировать/удалять до отмены проведения. Сам универсальный механизм движений/регистров в Iteration 001 не создаётся.

## 3. Бизнес-нумерация

| Объект | Область уникальности | Счётчик |
|---|---|---|
| Элемент справочника | `object_type_id` | `meta.catalog_counters` или эквивалентная строка счётчика типа |
| Документ | `object_type_id + calendar_year` | `meta.document_counters` |
| План | `object_type_id + calendar_year` | `meta.planning_counters` |

В реализации допускается одна физическая таблица счётчиков с ключом `(object_type_id, year)`; для справочника используется `year = 0`, для документов/планов — фактический `number_year`. Это внутренняя деталь Meta, а не публичная generic numbering subsystem. Логически области счёта остаются раздельными по видам объектов.

Алгоритм выдачи номера — только внутри транзакции: `INSERT ... ON CONFLICT ... DO UPDATE SET last_number = counter.last_number + 1 RETURNING last_number`. Первое значение создаётся как 1. Строка счётчика блокируется PostgreSQL на время операции; уникальное ограничение на таблице объекта служит последней защитой. `MAX(number) + 1` запрещён. Счётчик не уменьшается при soft delete, физическом удалении или rollback после уже завершённой операции; при rollback выдача номера также откатывается, поскольку номер ещё не был зафиксирован.

Уникальность: для справочника `(code)` внутри физической таблицы типа; для документа `(number_year, number)`; для плана `(number_year, number)`. Номера не переиспользуются. Изменение выданного номера или даты, влияющей на год, выполняется отдельной явной операцией с блокировкой, проверкой уникальности и записью причины в аудит, когда аудит будет реализован. Обычное обновление реквизитов не меняет номер.

## 4. Формат конфигурации

Формат — UTF-8 JSON, `format_version` обязателен. Для первой реализации принимается `format_version: "1"`; версия конфигурации — SemVer `version`. Декодирование строгое: неизвестные поля запрещены (`DisallowUnknownFields`), дублирующиеся JSON-ключи/ID, некорректные UUID, неизвестные типы и неразрешённые ссылки отклоняются до DDL.

Минимальная структура:

```json
{
  "format_version": "1",
  "configuration": {
    "id": "8f4f7f8a-7d34-4e2f-9c6a-5a5c4c1a1001",
    "code": "example",
    "name": "Example configuration",
    "version": "1.0.0",
    "platform_compatibility": ">=0.2.0 <0.3.0"
  },
  "object_types": [
    {
      "id": "8f4f7f8a-7d34-4e2f-9c6a-5a5c4c1a2001",
      "kind": "catalog",
      "code": "locations",
      "name": "Locations",
      "attributes": [
        {
          "id": "8f4f7f8a-7d34-4e2f-9c6a-5a5c4c1a3001",
          "code": "name",
          "name": "Name",
          "type": "string",
          "length": 255,
          "required": true,
          "unique": false,
          "index": false
        }
      ]
    }
  ]
}
```

Пример иллюстрирует форму, не является встроенной конфигурацией. UUID должны быть стабильными между версиями и не генерироваться заново при переименовании.

### 4.1. Поля определения типа

`id` (UUID), `kind` (`catalog|document|planning|task|note`), `code` (стабильный машинный код внутри конфигурации), `name` (отображаемое имя), `attributes` (список реквизитов). Опциональные свойства вида: `hierarchy`, `folders`, `owner_type_id`, `numbering` и `posting`. Они допустимы только для соответствующего `kind`.

### 4.2. Поля реквизита

Обязательные: `id` UUID, `code`, `name`, `type`, `required`. Дополнительные — только применимые к типу:

- `string`: `length` (1..10 000); отображается в `VARCHAR(length)`;
- `text`: отображается в `TEXT`;
- `integer`: `BIGINT`;
- `decimal`: `precision` (1..38), `scale` (0..precision), `NUMERIC(p,s)`;
- `boolean`: `BOOLEAN`;
- `date`: `DATE`;
- `datetime`: `TIMESTAMPTZ`;
- `reference`: `target_type_id` UUID и `on_delete` из разрешённого набора `restrict`; физический FK на `data`-таблицу цели.

Для реквизитов разрешены `unique`, `index`, `default` только в ограниченном типизированном JSON-значении, `min`/`max` для чисел, `min_length`/`max_length` для строк. Составной индекс/уникальность описывается отдельным объектом `indexes` с ID, списком attribute UUID, `unique` и `where_active` (для частичного уникального индекса активных строк). Никаких SQL-выражений, имён колонок или произвольных предикатов из конфигурации.

### 4.3. Ссылки и циклы

Ссылка обязана указывать на существующий `target_type_id` в той же установленной конфигурации. Ссылки на `catalog`, `document`, `planning`, `task` и `note` разрешены при наличии совместимого физического FK. Полиморфная ссылка на набор типов запрещена. Для обычных ссылок — `ON DELETE RESTRICT`; каскад допускается только для дочерних строк табличной части/композиции, если такой механизм отдельно определён типом. В первой схеме универсальные табличные части не вводятся.

Циклические ссылки между объектными типами допустимы на уровне FK после создания всех таблиц: DDL установщика сначала создаёт таблицы без межтабличных FK, затем добавляет FK отдельной фазой. Самоссылка допустима, если тип и реквизит это явно задают.

## 5. Физическая схема PostgreSQL

### 5.1. Схемы

- `meta` — реестр конфигураций, версий, типов, реквизитов, actor и счётчиков.
- `data` — физические таблицы сохраняемых типов конфигурации.
- `public.schema_migrations` — существующий реестр SQL-миграций приложения, поскольку текущий migration runner создаёт его именно в `public`; не переименовывать его в рамках проектирования.

### 5.2. Минимальные таблицы Meta

| Таблица | Назначение | Ключевые поля и ограничения |
|---|---|---|
| `meta.actors` | Минимальная цель FK авторства/исполнителя | `id BIGINT PK`, `code TEXT UNIQUE NOT NULL`, `name TEXT NOT NULL`, `is_active BOOLEAN NOT NULL` |
| `meta.configurations` | Зарегистрированная конфигурация | `id UUID PK`, `code TEXT UNIQUE`, `name TEXT`, `installed_version TEXT NULL`, `created_at`, `updated_at` |
| `meta.configuration_versions` | Неизменяемые исходные JSON-версии | `configuration_id UUID FK`, `version TEXT`, `format_version TEXT`, `document JSONB`, `checksum TEXT`, `installed_at TIMESTAMPTZ`; PK `(configuration_id, version)` |
| `meta.object_types` | Нормализованный индекс метаданных установленных типов | `id UUID PK`, `configuration_id UUID FK`, `kind`, `code`, `name`, `physical_table`, `active`; UNIQUE `(configuration_id, code)` и `physical_table` |
| `meta.attributes` | Нормализованный индекс реквизитов | `id UUID PK`, `object_type_id UUID FK`, `code`, `name`, `data_type`, `physical_column`, `required`, `reference_type_id UUID NULL`; UNIQUE `(object_type_id, code)` и `(object_type_id, physical_column)` |
| `meta.number_counters` | Атомарное резервирование номеров | PK `(object_type_id, year)`, `last_number BIGINT NOT NULL CHECK (last_number >= 0)`, FK на `object_types` |

Исходный JSONB версии — канонический документ конфигурации. Нормализованные `object_types` и `attributes` — индекс для Runtime/DDL и проверки FK, не альтернативный источник редактирования. Все изменения выполняются через установщик и записывают новую версию конфигурации. `installed_version` меняется только после успешной установки.

`indexes` и полные определения ограничений сохраняются в JSONB исходной версии; в первой итерации отдельная таблица для индексов не нужна, поскольку установщик может воспроизвести их из проверенного документа. При появлении runtime-запросов метаданных отдельная таблица добавляется только по доказанной необходимости.

### 5.3. Физические таблицы объектов

Каждый тип получает таблицу `data.o_<uuid_without_hyphens>`; каждый реквизит — колонку `a_<uuid_without_hyphens>`. UUID гарантирует стабильность имени и не зависит от `code`/`name`; длина имени ниже лимита PostgreSQL в 63 байта. Идентификаторы SQL всегда формируются из проверенного UUID и экранируются как идентификаторы драйвером/внутренним helper; значения передаются параметрами. Строки конфигурации не подставляются в SQL как фрагменты.

Обязательные системные колонки: `id`, `created_at`, `updated_at`, `created_by`, `updated_by`, `deleted_at`. Дополнительно — колонки стандартного типа и реквизиты конфигурации. PK — `id`; FK author на `meta.actors`; FK reference на `data.o_<target_uuid>(id)`. Для обычного FK — `ON DELETE RESTRICT`. `created_by`/`updated_by` используют `ON DELETE RESTRICT` (actor не удаляется физически при наличии истории).

Индексы создаются только по метаданным: PK, FK-supporting indexes, уникальные индексы, явно объявленные индексы. FK в PostgreSQL не создаёт индекс на ссылающейся колонке автоматически — установщик создаёт его явно. Для уникальности активных значений `where_active=true` используется `UNIQUE ... WHERE deleted_at IS NULL`; по умолчанию бизнес-номера уникальны среди всех строк, включая soft-deleted, чтобы номер нельзя было переиспользовать.

### 5.4. Порядок создания

1. SQL-миграции создают schema `meta`, schema `data`, `meta.actors`, реестр конфигураций/версий, типы/атрибуты, счётчики.
2. Установщик проверяет JSON и совместимость с версией платформы; строит неизменяемый план DDL.
3. Создаются все таблицы объектных типов с системными и собственными колонками, без межтабличных FK.
4. Создаются индексы, `CHECK`, `UNIQUE` и межтабличные FK после того, как все таблицы существуют.
5. Записываются нормализованные метаданные и JSON-версия; обновляется `installed_version` последним действием транзакции.

Первичные системные таблицы и метаданные создаются обычными SQL-миграциями проекта. Таблицы конкретных объектных типов создаются установщиком из конфигурации, а не ручными migration-файлами на каждый вид.

## 6. Эволюция конфигурации

Обновление всегда начинается с `plan` (dry-run): сравнение UUID и типов с установленной версией, проверка данных, выдача списка DDL и классификация каждого действия. Применение возможно только после успешной проверки плана. Операция сериализуется PostgreSQL advisory lock на `configuration_id`.

| Изменение | Класс | Правило |
|---|---|---|
| Добавить тип | Безопасное | Создать новую пустую таблицу и метаданные |
| Добавить nullable-реквизит | Безопасное | Добавить nullable-колонку |
| Добавить required-реквизит | Условно безопасное | Разрешено для пустой таблицы; для непустой — только с явным default/backfill и проверкой, иначе блокировать |
| Переименовать `name`/`code` при сохранении UUID | Безопасное | Обновить отображаемые метаданные; физическое имя не меняется |
| Переименовать UUID реквизита/типа | Несовместимое | Считать удалением + добавлением; запрещать автоматическое сопоставление |
| Изменить длину строки вверх | Безопасное | `ALTER COLUMN TYPE VARCHAR(n)` после проверки совместимости |
| Изменить длину вниз | Разрушительное | Запретить без отдельного transform/backfill и отчёта о строках, превышающих лимит |
| Изменить тип | Разрушительное/условное | Никакого автоматического CAST; требуется явное преобразование, dry-run и резервная копия |
| Изменить `required=false` на `true` | Условное | Проверить NULL; backfill обязателен, затем `SET NOT NULL` |
| Удалить реквизит | Разрушительное | По умолчанию колонку не удалять: пометить metadata deprecated/inactive и скрыть из Runtime; физическое удаление только отдельной подтверждённой миграцией после экспорта/архива |
| Удалить тип | Разрушительное | Запретить при строках/входящих FK; деактивировать тип; физическое удаление отдельной подтверждённой операцией |
| Изменить ссылочную цель | Разрушительное/условное | Проверить все значения и преобразование; FK не переключать молча |
| Удалить индекс | Безопасное по данным | Удалить только индекс после проверки зависимостей |

Неизвестные изменения и downgrade конфигурации отклоняются. Неизменяемые UUID сохраняются между версиями. Старые JSON-версии не перезаписываются. Любое преобразование данных имеет явный план и проверяемый результат. В первой реализации автоматический destructive transform не поддерживается.

## 7. Ссылки, удаление и жизненный цикл

- FK обеспечивает физическую ссылочную целостность; soft delete не нарушает FK и не каскадирует.
- Обычные пользовательские выборки скрывают `deleted_at IS NOT NULL`; административная выборка может явно включать их.
- Нельзя soft-delete объект, если он проведён; сначала выполняется отмена проведения.
- Нельзя физически удалить объект с входящими ссылками; стандартное действие — RESTRICT.
- Каскад разрешён только для принадлежащих владельцу дочерних строк, не для самостоятельных объектов. Табличные части не входят в первую схему.
- Проведение и отмена проведения — сервисные транзакционные команды. Они не равны удалению и не реализуют универсальный workflow.

## 8. Первая схема и порядок реализации

Первая SQL-схема должна содержать только `meta.actors`, `meta.configurations`, `meta.configuration_versions`, `meta.object_types`, `meta.attributes`, `meta.number_counters`, а также необходимые schema `meta` и `data`. Физические таблицы конфигурации создаются только тестовой fixture-конфигурацией в интеграционных тестах/установщике. Не добавлять IAM, audit log, registers, workflow, generic numbering service, EAV, tabular sections, attachments или GigaWatt-типы.

Существующие `meta_catalogs`, `meta_catalog_elements` и миграции 000002/000003 принадлежат прежней реализации DITA 0.1.0/раннему прототипу. В рамках документальной итерации их не изменять. Для чистой схемы DITA 0.2.0 требуется отдельное решение о миграционном baseline и точной целевой БД; не переносить и не сбрасывать данные автоматически.
